# v1.2.1 修复报告、修改边界与验收方法

日期：2026-09-19（Asia/Shanghai）。对比基线：`v1.2.0 / e92fcc2`。本报告不包含测试服务器地址、客户 Token、密码或数据库 DSN。真实环境凭据仍使用已有配置，不在 Git 中分发。

## 1. 结论与发布范围

本次修复三项回执可靠性问题，同时恢复客户 DR 的 HTTP/HTTPS 双协议兼容，并降低空队列轮询压力。三项问题与 v1.2.0 的可靠性改造有关，不能笼统归为历史问题。本次不修改鉴权、租户额度口径、路由权重、短信编码与供应商提交重试策略。

长短信分片固定路由已在 v1.2.0 实现；本次补充更完整的回归与现场验证，没有重新设计路由算法。测试环境只替换 mysmpp 容器，并增加一个 PostgreSQL 索引，其他已有服务没有重启。

**验收状态必须区分：代码回归通过，SMPP 现场链路通过；现有公网 HTTP 回调地址仍连接超时，尚未完成该地址的端到端验收。** 新版本已接受 HTTP URL，HTTP 接收应用本机 OPTIONS/POST 正常，但网关无法连上其公网端口。相关 4 条测试回执保留在 delivery pending 中重试；没有把它们改成成功，没有重发短信，也没有绕开回调地址安全策略。

## 2. 修改内容及边界

| 项目 | 原问题 | 本次处理 | 影响边界 |
|---|---|---|---|
| 到期清理 | 每轮有限批次，持续新增时可能积压；未完成消息逐条事务吞吐低 | 有时间预算地连续清理多批；完整终态组批量删除；未完成组最多 4 个事务并发生成 EXPIRED 快照 | 仅 pending、receipt_jobs、multipart_bindings 到期维护，不清理 messages/CDR 历史数据 |
| SMPP 接收 | readLoop 同步等待回执落库，慢数据库阻塞 submit_sm_resp/心跳读取 | 每连接 128 个待处理槽位与 1 个回执落库 worker，接收循环只入队；落库成功再 ACK | 不改窗口、客户 submit 状态码、上游发送重试与编码 |
| inbox/过期竞争 | DLR 已持久化但未处理，pending 被清理后误推 EXPIRED | inbox 入库与过期决策都先锁 messages 行；pending/claimed inbox 阻止该组过期 | 精确按 provider + provider_id 找映射，保留跨供应商 ID 隔离 |
| HTTP 回调 | v1.2.0 入口和投递仅允许 HTTPS | 共用 URL 校验同时允许 HTTP/HTTPS | 不新增默认 URL；不改历史回调地址；HTTPS 仍验证证书，禁止跳转和内网连接 |
| 空轮询 | 无业务时仍高频访问数据库 | 空队列指数退避，常规上限 250ms；有任务恢复原周期 | 不改配置中的 workers/TPS；冷启动每个队列阶段可能多约 250ms 等待 |
| 长短信路由 | 客户预拆片必须保持同一通道 | 保留已有持久化分片绑定，新增 UDH8/UDH16/SAR 乱序、跨会话、热改路由测试 | 每个 submit_sm 仍有独立 gateway_id/额度/DR，不改成逻辑长短信聚合 |

### 2.1 清理容量与事务

终态完整组每条 SQL 最多选 10,000 个 gateway 组，未完成组每页 1,000 个 gateway、最多 4 个并发事务。每条消息仍在独立事务中完成行锁、状态聚合、快照写入和映射删除。活动 inbox 在候选扫描时过滤，并在消息行锁内再次核对，避免竞态。大批活动 inbox 不应因不断重复选中而占满清理预算。

managed pending 清理循环预算 15 秒，SweepExpiredPending 总 context 上限 25 秒；旧记录清理循环预算 5 秒。SweepReliability 循环预算 15 秒、context 上限 20 秒。预算控制下一批开始，不保证正在执行的 SQL 恰好在预算时刻结束；由 context 进一步限制。任务清理不删除仍持有效租约的 claimed 任务。时间预算耗尽后剩余记录等下一轮，不创建无上限协程。

新索引 `009_receipt_inbox_expiry_index` 针对 `kind=inbox` 且 `state=pending/claimed` 的 JSON Provider/ProviderID 映射。迁移只加索引，不改业务列、租户或密码。部署时使用短锁等待和语句超时，索引成功后才替换网关。

隔离 PostgreSQL 测试先暴露出未完成组单线程在 15 秒只处理 7,447/12,050 条的不足；增加有上限的 4 路处理后，相同测试约 10.86 秒全部完成。完整终态路径清理 12,050 个 pending + 24,100 个任务约 0.17 秒。测试数据库限制为 1 CPU/512MB、tmpfs 数据盘，不能将该耗时视为生产磁盘或持续业务压力下的 SLA。

### 2.2 SMPP ACK 与重连

1. 收到合法 DLR 后入当前连接专属队列。
2. 工作线程持久化成功，才发送 status=0 的 deliver_sm_resp。
3. 队列满或落库失败，返回 `ESME_RSYSERR=0x00000008`，由上游重推。没有成功落库却提前成功 ACK。
4. 队列、回复通道和 worker 都绑定本次连接；断连时关闭本次通道并等待 worker 退出，不向新会话写旧 ACK。
5. 生产持久化回调有 3 秒 context 超时。未 ACK 的排队回执在连接关闭后依赖上游重投，不承诺不重试的供应商也能无损。

此处改的是网关作为上游 SMPP 客户端接收 DLR 的循环，不是关闭客户 DR。已经受理消息的 DR 仍不经过客户 TPS/日额度准入检查。

### 2.3 同一长短信依据什么绑定

绑定键由租户/账号、源地址、目的地址、DCS，以及 UDH8/UDH16 或 SAR 的拼接引用信息共同构成；UDH 中其他 IE 信息也参与隔离。不能只用“相同 reference”跨客户归组，更不能用 gateway_id 归组，因为客户每个 submit_sm 都会取得不同 gateway_id。

首次到达的分片（不要求 part=1）确定路由和供应商，后续分片沿用。有效期 10 分钟；相同组改变总片数或同一片内容冲突时拒绝。跨会话/正常持久化重启后继续使用已有绑定；原路由/供应商被禁用或移除时拒绝后续片，不换供应商补发。

边界：没有 UDH/SAR 拼接信息就不能可靠识别“同一条长短信”。绑定超时后的片也不承诺沿用旧绑定。原始预拆片的每个 submit_sm 仍分别计额和回 DR，不能把 HTTP 网关自拆片的 `segment_count=3` 与三个独立 SMPP submit 的 `segment_count=1` 混为一谈。

## 3. HTTP 配置与现有参数

不存在全局“DR 默认 HTTP”开关。客户按下面模板传入 **HTTP** callback_url 即按 HTTP POST JSON，不自动改为 HTTPS；省略则不会凭空生成回调地址。已受理消息、delivery 快照中的地址不会因升级或幂等重试而改变。

```bash
curl --fail-with-body "http://${MYSMPP_HOST}:19087/v1/messages" \
  -H 'Content-Type: application/json' \
  -H 'X-Client-ID: tenant-c' \
  -H "X-Token: ${TENANT_C_TOKEN}" \
  --data "{\"from\":\"TestBrand\",\"to\":\"+8613800138000\",\"text\":\"HTTP callback test\",\"client_msg_id\":\"new-unique-test-id\",\"callback_url\":\"http://${CALLBACK_PUBLIC_HOST}:2761/sl_callback/callback/sms_report\",\"callback_rule\":\"reliability-test\"}"
```

变量由测试人员从已有测试配置取得。测试号码仅用于已确认通向测试桩的 tenant-c，不应直接复制到真实短信路由。每次新测试换 client_msg_id；同业务重试复用该 ID。相同 ID 返回同 gateway_id，不新增短信/日额度。

HTTP URL 仍须是完整公网地址，禁止 URL 用户名密码、fragment、重定向及实际解析为内网/回环/链路本地的地址。HTTP 是明文传输；HTTPS 继续使用证书校验与最低 TLS 1.2。此次没有把内网地址加入白名单，也没有提供回调签名功能。

| 租户 | HTTP/SMPP 账号 | TPS / burst | 单日受理分片限额 | 时区 |
|---|---|---:|---:|---|
| tenant-a | tenant-a / tenant-a | 80 / 80 | 1000 | Asia/Shanghai |
| tenant-b | tenant-b / tenant-b | 60 / 60 | 500 | Asia/Shanghai |
| tenant-c | tenant-c / tenant-c | 40 / 40 | 不限 | Asia/Shanghai |

## 6. 回滚与明确未解决的事项

v1.2.0 只接受 HTTPS；已经有 HTTP delivery 任务后不能无评估直接回滚，否则这些任务可能被旧协议校验拒绝。优先修复前进。确需回滚时先核对队列和 HTTP 客户，保留任务/备份，不能执行删除可靠性表的 down migration。009 只加索引，回滚二进制无须删除该索引。

此次没有承诺“所有情况下完全没问题”。明确边界如下：

1. 现有公网 HTTP 回调网络验收尚未通过；未修改其他服务、共享防火墙或放开内网访问。需要可达的公网接收地址或恢复原端口可达性。
2. 未在业务库上做持续 200 TPS 压测或故障注入。清理批量回归证明指定隔离夹具能处理，不证明任意长度短信、全部慢回调及长期磁盘压力下都够用。
3. HTTP/SMPP 客户回执至少一次，客户仍应按 delivery_id 或自己的业务键幂等；慢/离线客户耗尽共享回执 worker 的公平性隔离未改。
4. memory 重启丢数据；file 正常保存后可恢复，但磁盘写失败的原子保证不等同于 PG。本次环境使用 PG。
5. 历史 34 条 ready SMPP 和 30 条旧 HTTP pending 没有批量补推或改写；原有到期策略仍然适用。
6. 配置接口先改运行时再写文件、CDR dlr 记录时机等先前发现的独立问题不在本次三项修复内，不能宣称已解决。

测试人员可以据本报告复验；不能仅用 HTTP 202、messages=DELIVRD 或上游 DLR 到达判断客户已收到 DR，必须同时核对 delivery 状态与客户接收记录。
