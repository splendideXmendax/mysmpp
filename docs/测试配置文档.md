# 测试环境租户限流限额配置

更新时间：2026-08-24（Asia/Shanghai）

本文记录测试环境当前已生效的租户绑定、TPS、日额度和路由配比。账号密码、Token、Provider 凭据等敏感信息不在本文记录。

## 1. 短信分片口径

分片就是一条短信实际占用的短信段数。短短信通常是 1 个分片，超过单段容量后会拆成长短信的多个分片。

| 编码 | 单段容量 | 长短信每段容量 | 示例 |
|---|---:|---:|---|
| GSM-7 | 160 septets | 153 septets | 160 个普通 GSM-7 字符为 1 段，161 个为 2 段 |
| UCS-2 | 70 个 UTF-16 code units | 67 个 UTF-16 code units | 70 个普通中文字符为 1 段，71 个为 2 段 |

补充说明：

- GSM-7 扩展表字符占 2 个 septets，不能简单按字符个数计算。
- Emoji 通常占 2 个 UTF-16 code units，例如 35 个常见 Emoji 为 1 段，36 个通常为 2 段。
- 日额度按网关受理时计算的理论分片数扣减，不按 API 请求次数扣减。
- 一条 3 分片短信会消耗 3 个 `daily_segments`。
- 整条消息一次性占用额度。例如当天还剩 1 个分片时提交 2 分片短信，整条都会被拒绝。
- 已受理消息即使后续上游发送失败也不返还额度。
- HTTP 使用相同 `client_msg_id` 的幂等重试不会重复扣减额度。
- 上游 `long_message: payload` 只发送一个 SMPP PDU 时，额度仍按理论短信分片数保守扣减。

## 2. 当前租户配置

| 主租户 | HTTP 子账号 | SMPP 子账号 | TPS | Burst | 每日分片额度 | 时区 |
|---|---|---|---:|---:|---:|---|
| `tenant-a` | `tenant-a` | `tenant-a` | 80 | 80 | 1000 | `Asia/Shanghai` |
| `tenant-b` | `tenant-b` | `tenant-b` | 60 | 60 | 500 | `Asia/Shanghai` |
| `tenant-c` | `tenant-c` | `tenant-c` | 40 | 40 | 不限制 | `Asia/Shanghai` |
| `tenant-ap2` | 无 | `ap2-esme` | 20 | 20 | 不限制 | `Asia/Shanghai` |
| **合计** |  |  | **200** | **200** |  |  |

同一主租户下的 HTTP 和 SMPP 子账号共享 TPS、Burst 和每日分片额度。例如 `tenant-b` 的 HTTP 与 SMPP 流量合计不能持续超过 60 TPS，两种协议的受理分片数合计不能超过每天 500。

`200 TPS` 是四个租户配置上限之和，不是动态共享的全局令牌桶。某租户未使用的 TPS 不会自动借给其他租户。

TPS 使用进程内令牌桶实现。当前测试环境为单实例，因此配置值就是该实例上的租户速率；Burst 表示桶满时可立即使用的最大令牌数。

### 2.1 当前实际生效的租户 JSON

线上配置中的 `tenants` 内容如下。`enabled=true` 表示主租户可受理请求；`daily_segments=0` 表示不设置日额度，不是额度为 0：

```json
{

    {
      "tenant_id": "tenant-a",
      "enabled": true,
      "limits": {
        "tps": 80,
        "burst": 80,
        "daily_segments": 1000,
        "timezone": "Asia/Shanghai"
      }
    },
    {
      "tenant_id": "tenant-b",
      "enabled": true,
      "limits": {
        "tps": 60,
        "burst": 60,
        "daily_segments": 500,
        "timezone": "Asia/Shanghai"
      }
    },
    {
      "tenant_id": "tenant-c",
      "enabled": true,
      "limits": {
        "tps": 40,
        "burst": 40,
        "daily_segments": 0,
        "timezone": "Asia/Shanghai"
      }
    },
    {
      "tenant_id": "tenant-ap2",
      "enabled": true,
      "limits": {
        "tps": 20,
        "burst": 20,
        "daily_segments": 0,
        "timezone": "Asia/Shanghai"
      }
    }
  ]

```

HTTP 和 SMPP 子账号必须显式填写相同 `tenant_id`，才能共享主租户限制。线上绑定关系等价于：

```json
{
  "clients": [
    {"client_id": "tenant-a", "tenant_id": "tenant-a", "enabled": true},
    {"client_id": "tenant-b", "tenant_id": "tenant-b", "enabled": true},
    {"client_id": "tenant-c", "tenant_id": "tenant-c", "enabled": true}
  ],
  "esmes": [
    {"system_id": "ap2-esme", "tenant_id": "tenant-ap2", "enabled": true},
    {"system_id": "tenant-a", "tenant_id": "tenant-a", "enabled": true},
    {"system_id": "tenant-b", "tenant_id": "tenant-b", "enabled": true},
    {"system_id": "tenant-c", "tenant_id": "tenant-c", "enabled": true}
  ]
}
```

上面的片段故意省略 Token 和密码。它是说明绑定关系的局部片段，不能直接作为 `/v1/config` 请求体提交；配置 API 要求提交完整配置。

### 2.2 租户、账号和协议之间的关系

```text
tenant-a
  HTTP client tenant-a --+
  SMPP ESME  tenant-a ----+--> 共享 80 TPS、Burst 80、每日 1000 分片

tenant-b
  HTTP client tenant-b --+
  SMPP ESME  tenant-b ----+--> 共享 60 TPS、Burst 60、每日 500 分片

tenant-c
  HTTP client tenant-c --+
  SMPP ESME  tenant-c ----+--> 共享 40 TPS、Burst 40、不限日额度

tenant-ap2
  SMPP ESME ap2-esme --------> 20 TPS、Burst 20、不限日额度
```

主租户负责策略，子账号负责鉴权和协议身份：

| 层级 | 主要字段 | 职责 |
|---|---|---|
| 主租户 | `tenant_id`、`enabled`、`limits` | 控制统一 TPS、Burst、日额度和计费时区 |
| HTTP 子账号 | `client_id`、`token`、`tenant_id` | HTTP 鉴权、HTTP 幂等作用域、绑定主租户 |
| SMPP 子账号 | `system_id`、`password`、`tenant_id` | SMPP bind 鉴权、DLR 回推身份、绑定主租户 |

如果 HTTP/SMPP 子账号没有配置 `tenant_id`，系统会兼容性地生成独立身份 `http:<client_id>` 或 `smpp:<system_id>`，默认不限 TPS、不限日额度。这个回退行为用于兼容旧配置，不应作为正式租户配置使用。

如果子账号引用了不存在的 `tenant_id`，该身份会按禁用处理并拒绝提交，避免由于拼写错误绕过额度。

### 2.3 租户限制字段语义

| 字段 | `0` 的含义 | 正数的含义 | 当前约束 |
|---|---|---|---|
| `limits.tps` | 不限 TPS | 每秒连续补充的令牌数 | 不能为负数 |
| `limits.burst` | 当 TPS 大于 0 时自动等于 TPS | 令牌桶最大容量 | TPS 为 0 时 Burst 不能大于 0 |
| `limits.daily_segments` | 不限制每日分片数 | 主租户自然日硬上限 | 不能为负数 |
| `limits.timezone` | 使用 UTC | 依据该时区划分自然日 | 必须是有效 IANA 时区名称 |
| `enabled` | 显式 `false` 才禁用 | `true` 或省略均启用 | 禁用后 HTTP/SMPP 都拒绝提交 |

当前四个租户都配置 `Asia/Shanghai`，因此日额度按北京时间自然日计算：`00:00:00` 开始新额度日，到次日 `00:00:00` 切换。

### 2.4 TPS 限频的准确行为

TPS 使用进程内、按 `tenant_id` 建立的令牌桶：

1. 首次请求或配置热加载后，桶内初始令牌数等于 `burst`。
2. 每经过一段时间，按 `tps × elapsed_seconds` 连续补充令牌。
3. 桶内令牌最多达到 `burst`，空闲期间不会无限累积。
4. 每个提交请求在进入内容过滤、路由、号码校验前先消耗 1 个令牌。
5. HTTP 和 SMPP 只要解析到同一个 `tenant_id`，就访问同一个桶。
6. 没有令牌时立即拒绝，不进入消息、outbox，也不调用 Provider。

它不是固定的一秒窗口。例如 `tenant-c` 配置 `tps=40, burst=40`：

- 桶满时可瞬间通过最多 40 个请求。
- 之后平均每 25ms 补充约 1 个令牌。
- 100 个并发请求如果执行耗时 50ms，可能有约 42 个通过桶，而不是严格固定为 40 个。
- 长期稳定吞吐仍被约束在约 40 TPS。

TPS 对“提交请求”计数，不按短信分片计数。一条 10 分片长短信消耗 1 个 TPS token，但会消耗 10 个日额度分片。

正常路径中的 HTTP 幂等重试也会先消耗一个 TPS token，然后在数据库事务中命中幂等记录。如果当时已经被 TPS 限流，系统会额外查询 `client_msg_id`；已存在的幂等请求仍返回原 `gateway_id`，避免客户端因拿不到原结果持续重试。

当前 TPS limiter 只在单进程内精确。测试环境只有一个 mysmpp 实例，所以生效值就是配置值；如果将来运行 N 个实例且没有外部共享 limiter，总 TPS 约为配置值乘以 N。

### 2.5 日额度的准确行为

日额度使用 PostgreSQL 表 `tenant_quota_usage` 的单行原子计数，唯一键是：

```text
(tenant_id, quota_date)
```

受理一条消息时，数据库事务顺序固定为：

```text
HTTP 幂等键
  -> 租户日额度原子增加
  -> messages 写入
  -> outbox 写入
  -> COMMIT
```

因此具有以下保证：

- 幂等冲突在额度操作之前返回，相同 HTTP `client_msg_id` 不重复扣额度。
- 额度增加、message 和 outbox 在同一个事务里提交，任何一步失败都会整体回滚。
- 并发请求对同一个租户/日期的计数是原子的，不会因为并发检查产生超额受理。
- `used_segments + 本次分片数 > daily_segments` 时整条拒绝，不会只受理一部分分片。
- 单条消息自身的分片数大于日额度时也会直接拒绝。

额度扣减时点是“网关成功受理并写入消息/outbox”，不是“上游送达成功”。后续 Provider 拒绝、超时、未送达或进入 `UNKNOWN` 都不会返还额度。这是防止通过失败重试绕过硬上限的保守策略。

当前按网关编码器计算的理论短信分片数扣减：

| 提交内容 | TPS 消耗 | 日额度消耗 |
|---|---:|---:|
| 1 条单段短信 | 1 | 1 分片 |
| 1 条 3 分片长短信 | 1 | 3 分片 |
| 相同 HTTP `client_msg_id` 幂等重试 | 会经过 TPS | 0 个新增分片 |
| 验证失败、路由失败 | 可能已消耗 TPS | 0 个分片 |
| 已受理后上游失败 | 已消耗 | 不返还 |

SMPP 客户端自己预切的 3 个独立 `submit_sm` 会被视为 3 条独立消息，各自消耗 1 个 TPS token；每个请求按自身解析出的分片数扣额度。网关不会仅凭短信内容猜测它们属于同一客户长短信。

### 2.6 一次提交的完整生效顺序

```text
HTTP Token / SMPP bind 鉴权
  -> 根据 protocol + account_id 解析主租户
  -> 检查 tenant.enabled
  -> 主租户 TPS 令牌桶
  -> 内容过滤
  -> 路由匹配
  -> 目标号码校验
  -> 生成 gateway_id
  -> 按 gateway_id 加权选择 Provider
  -> 编码与理论分片计算
  -> PostgreSQL 幂等判断
  -> PostgreSQL 日额度原子扣减
  -> message + outbox 原子写入
  -> HTTP 202 / SMPP submit_sm_resp ESME_ROK
  -> Dispatcher 异步调用上游
  -> DLR 聚合、HTTP callback 或 SMPP deliver_sm
```

从这个顺序可推导：

- 错误密码不会消耗 TPS 或额度。
- 租户禁用不会消耗 TPS 或额度。
- 号码无效可能消耗 TPS，但不会消耗日额度。
- 额度超限会消耗一次 TPS token，但不会创建 message/outbox。
- HTTP 202 和 SMPP `ESME_ROK` 表示已经占用额度并入队，不代表送达。

### 2.7 “总 200 TPS”的准确解释

当前 `80 + 60 + 40 + 20 = 200 TPS` 是四个独立租户上限的算术合计：

- 它不是额外的一层全局 200 TPS gate。
- tenant-a 空闲时，tenant-b 仍不能超过 60 TPS。
- 四个租户都持续跑满时，单实例总受理速度约为 200 TPS。
- 突发瞬间四个桶合计最多有 200 个初始 token。
- 如果需要“任何租户可借用空闲容量，但全系统绝不能超过 200 TPS”，还需要独立的全局令牌桶；当前配置没有这个能力。

当前测试入口是明文 HTTP 和明文 SMPP。只允许在受控测试网络中使用；公网传输会暴露 Token、密码和短信内容。正式客户接入前应配置 HTTPS/TLS、来源 IP 白名单或专网/VPN。

### 8.1 当前线上 HTTP 鉴权模式

当前线上 `clients[]` 非空，配置了 `tenant-a`、`tenant-b`、`tenant-c` 三个 HTTP client。因此，`POST /v1/messages` 和 `GET /v1/messages` 必须同时携带以下两个请求头：

```http
X-Client-ID: tenant-b
X-Token: <tenant-b 对应的 HTTP Token>
```

两个请求头缺少任意一个、账号不存在、账号被禁用或 Token 不匹配，都会返回 `401 Unauthorized`。

下面这种写法在当前线上消息接口中无效：

```http
Authorization: Basic <credentials>
Content-Type: application/json
```

此时服务返回：

```text
401 Unauthorized
client credentials are required
```

原因不是 Base64 编码错误，而是消息接口检测到 `clients[]` 非空后只读取 `X-Client-ID` 和 `X-Token`，不会用 `Authorization: Basic` 代替 client 鉴权。

Basic Auth 的适用范围：

| 接口/模式 | 当前是否适用 Basic Auth |
|---|---|
| `/v1/config`、`/ui/config` | 是，始终使用管理员 Basic Auth |
| `/admin/` | 使用管理员网页登录会话，不使用 client Token |
| `/v1/messages` 且 `clients[]` 非空 | 否，必须使用 `X-Client-ID` + `X-Token` |
| `/v1/messages` 且 `clients[]` 为空 | 是，才会回退到管理员 Basic Auth 兼容模式 |

不要为了让测试代码继续使用 Basic Auth 而清空 `clients[]`。这样会取消 HTTP 子账号隔离和主租户绑定，使 A/B/C 无法按当前设计共享对应租户的 TPS 和日额度。

### 8.2 Python `requests` 正确鉴权示例

测试代码应从环境变量读取 Token，不要把真实 Token 写进 Python 文件：

```python
import os
import time

import requests


base_url = f"http://{os.environ['MYSMPP_HOST']}:{os.environ['MYSMPP_HTTP_PORT']}"
headers = {
    "X-Client-ID": os.environ["MYSMPP_TENANT_B_HTTP_CLIENT_ID"],
    "X-Token": os.environ["MYSMPP_TENANT_B_HTTP_TOKEN"],
    "Content-Type": "application/json",
}
payload = {
    "from": "10690000",
    "to": "13800138000",
    "text": "Python HTTP test message",
    "client_msg_id": f"qa-python-{time.time_ns()}",
    "meta": {
        "test_case": "python-http-basic",
    },
}

response = requests.post(
    f"{base_url}/v1/messages",
    headers=headers,
    json=payload,
    timeout=10,
)
print("status:", response.status_code)
print("body:", response.text)
response.raise_for_status()
```

不要同时传 `auth=(username, password)` 或手工设置 `Authorization: Basic ...`。虽然多余的 `Authorization` 头不会替代 client 鉴权，但它容易让排查人员误以为消息接口在使用管理员账号。

如果返回 `401 client credentials are required`，优先检查 Header 名称是否准确、有无被代理删除，以及环境变量是否加载：

```python
import os

for name in (
    "MYSMPP_TENANT_B_HTTP_CLIENT_ID",
    "MYSMPP_TENANT_B_HTTP_TOKEN",
):
    print(name, "loaded" if os.environ.get(name) else "missing")
```

该检查只输出 `loaded/missing`，不会把 Token 打印到日志。

### 9.2 PowerShell 提交示例

下面使用 `tenant-b`。它只路由到测试 stub，适合功能测试：

```powershell
$baseUrl = "http://${env:MYSMPP_HOST}:$($env:MYSMPP_HTTP_PORT)"
$headers = @{
    'X-Client-ID' = $env:MYSMPP_TENANT_B_HTTP_CLIENT_ID
    'X-Token'     = $env:MYSMPP_TENANT_B_HTTP_TOKEN
}
$clientMsgId = 'qa-http-' + [DateTimeOffset]::UtcNow.ToUnixTimeMilliseconds()
$body = @{
    from          = '10690000'
    to            = '13800138000'
    text          = 'HTTP test message'
    client_msg_id = $clientMsgId
    meta           = @{
        test_case = 'http-basic'
        operator  = 'qa'
    }
} | ConvertTo-Json -Depth 5

$receipt = Invoke-RestMethod `
    -Method Post `
    -Uri "$baseUrl/v1/messages" `
    -Headers $headers `
    -ContentType 'application/json' `
    -Body $body

$receipt | ConvertTo-Json -Depth 5
```

成功时 HTTP 状态为 `202 Accepted`，响应示例：

```json
{
  "gateway_id": "m0000abc",
  "provider_id": "",
  "provider": "stub-2779",
  "route": "tenant-b-http-weighted",
  "state": "queued"
}
```

`202` 只表示网关已受理并入队，不表示已经送达。调用方必须保存 `gateway_id`，后续通过查询或 DLR 回调确认最终状态。

### 9.4 HTTP 请求字段

| 字段 | 必填 | 规则 |
|---|---:|---|
| `from` | 是 | 1-32 个字符，并满足上游 source address 规则 |
| `to` | 是 | 11 位数字，或带 `+` 的 E.164 号码 |
| `text` | 是 | 非空，自动识别 GSM-7/UCS-2，最多 20 个分片 |
| `client_msg_id` | 否 | 客户业务 ID，1-64 个非空白字符；同一 HTTP client 下 24 小时幂等 |
| `callback_url` | 否 | 必须是完整 `https://` URL |
| `callback_rule` | 否 | 客户自定义回调标识，回调时原样返回 |
| `meta` | 否 | 最多 10 个键，每个值最多 200 个字符 |

### 9.5 幂等测试

将同一个 `$clientMsgId` 和相同请求体连续提交两次：

```powershell
1..2 | ForEach-Object {
    Invoke-RestMethod `
        -Method Post `
        -Uri "$baseUrl/v1/messages" `
        -Headers $headers `
        -ContentType 'application/json' `
        -Body $body
}
```

预期两次返回相同 `gateway_id`，数据库只新增一条消息，日额度只扣一次。`client_msg_id` 是 HTTP 客户端传入的业务 ID，不是 Provider ID。

### 9.6 查询当前 HTTP 账号的消息

PowerShell：

```powershell
$messages = Invoke-RestMethod `
    -Method Get `
    -Uri "$baseUrl/v1/messages?limit=20&offset=0" `
    -Headers $headers
$messages | ConvertTo-Json -Depth 10
```

Bash：

```bash
curl --fail-with-body \
  --header "X-Client-ID: ${MYSMPP_CLIENT_ID}" \
  --header "X-Token: ${MYSMPP_TOKEN}" \
  "http://${MYSMPP_HOST}:${MYSMPP_HTTP_PORT}/v1/messages?limit=20&offset=0"
```

HTTP client 只能查询自己的消息。常见状态：

| 状态 | 含义 |
|---|---|
| `queued` | 已受理，等待 Dispatcher 发送 |
| `sent` | 上游已成功返回 `submit_sm_resp` |
| `DELIVRD` | 最终送达成功 |
| `UNDELIV` / `EXPIRED` / `REJECTD` | 最终失败 |
| `failed` | 网关确认向上游提交失败 |
| `UNKNOWN` | 已调用上游但结果不确定；为避免重复发送不会自动重试 |

### 9.7 HTTP DLR 回调

提交时加入：

```json
{
  "callback_url": "https://client.example.com/sms/dlr",
  "callback_rule": "qa-http-dlr"
}
```

回调请求体示例：

```json
{
  "gateway_id": "m0000abc",
  "client_msg_id": "qa-http-001",
  "provider_id": "123456789",
  "provider": "stub-2779",
  "route": "tenant-b-http-weighted",
  "segment_index": 2,
  "segment_count": 3,
  "state": "DELIVRD",
  "message_state": "PENDING",
  "final": false,
  "error_code": 0,
  "done_at": "2026-08-21T02:00:00Z",
  "callback_rule": "qa-http-dlr"
}
```

接收端应返回任意 `2xx`，并按 `gateway_id + provider_id + state` 做幂等。只有 `final=true` 才表示同一 `gateway_id` 下所有上游分片都已进入最终态。

### 9.8 HTTP 常见错误

| HTTP 状态 | 典型原因 |
|---:|---|
| `400` | JSON/字段/目标号码无效，或超过 20 个分片 |
| `401` | `X-Client-ID` 或 `X-Token` 缺失/错误 |
| `403` | IP 白名单或内容过滤拒绝、租户禁用 |
| `429` | 主租户 TPS 或每日分片额度超限 |
| `502` | 无路由、存储或调度失败 |

### 10.3 Python `smpplib` 示例

安装成熟 SMPP 客户端库：

```bash
python -m pip install smpplib
```

保存为测试机上的 `smpp_submit.py`，密码从环境变量读取：

```python
import logging
import os

import smpplib.client
import smpplib.consts
import smpplib.gsm

logging.basicConfig(level=logging.INFO)

host = os.environ["MYSMPP_HOST"]
port = int(os.environ["MYSMPP_SMPP_PORT"])
system_id = os.environ["MYSMPP_TENANT_B_SMPP_SYSTEM_ID"]
password = os.environ["MYSMPP_TENANT_B_SMPP_PASSWORD"]


def on_deliver_sm(pdu):
    short_message = pdu.params.get("short_message", b"")
    if isinstance(short_message, bytes):
        text = short_message.decode("ascii", errors="replace")
    else:
        text = str(short_message)
    print("DLR:", text)


client = smpplib.client.Client(host, port)
client.set_message_received_handler(on_deliver_sm)
client.connect()
client.bind_transceiver(system_id=system_id, password=password)

parts, data_coding, esm_class = smpplib.gsm.make_parts("SMPP Python test")
for part in parts:
    pdu = client.send_message(
        source_addr_ton=smpplib.consts.SMPP_TON_INTL,
        source_addr_npi=smpplib.consts.SMPP_NPI_ISDN,
        source_addr="10690000",
        dest_addr_ton=smpplib.consts.SMPP_TON_INTL,
        dest_addr_npi=smpplib.consts.SMPP_NPI_ISDN,
        destination_addr="13800138000",
        short_message=part,
        data_coding=data_coding,
        esm_class=esm_class,
        registered_delivery=1,
    )
    print("submit sequence:", pdu.sequence)

# 阻塞等待 deliver_sm，并由库维护 SMPP 会话。
client.listen()
```

运行：

```bash
python smpp_submit.py
```

### 10.4 SMPP 长短信与额度

- 客户端发送一条未预切分的长短信时，应使用 UDH 或 SAR TLV 正确标识分片。
- 客户端已经预切成多个独立 `submit_sm` 时，网关会把它们视为多个独立消息和多个 `gateway_id`。
- 每个 `submit_sm` 都会消耗所属主租户的 TPS token。
- 日额度按每次受理的理论短信分片数扣减。
- SMPP 没有等同 HTTP `client_msg_id` 的标准业务幂等字段；断线重连后的重复提交可能被再次受理，客户侧需要对账。

### 10.5 SMPP 状态码

| `command_status` | 名称 | 含义 |
|---:|---|---|
| `0x00000000` | `ESME_ROK` | bind/submit 成功 |
| `0x0000000E` | `ESME_RINVPASWD` | SMPP 密码错误 |
| `0x0000000F` | `ESME_RINVSYSID` | `system_id` 不存在或禁用 |
| `0x0000000B` | `ESME_RINVDSTADR` | 目标号码无效 |
| `0x00000014` | `ESME_RMSGQFUL` | 网关提交队列已满 |
| `0x00000045` | `ESME_RSUBMITFAIL` | 路由、过滤或其他提交失败 |
| `0x00000058` | `ESME_RTHROTTLED` | 主租户 TPS、日额度或 SMPP 窗口超限 |

限频和日额度都映射为 `0x00000058`。客户端应做退避，不能在无间隔循环中立即重试，否则会持续占用连接和 CPU。

## 11. 限流与额度测试

### 11.1 安全的 HTTP TPS 测试

使用 `tenant-c` 和网关会拒绝的测试号码，可以验证 40 TPS 而不入队、不调用上游、不消耗日额度：

```bash
export MYSMPP_CLIENT_ID="$MYSMPP_TENANT_C_HTTP_CLIENT_ID"
export MYSMPP_TOKEN="$MYSMPP_TENANT_C_HTTP_TOKEN"

seq 1 100 | xargs -P100 -I{} curl --silent --output /dev/null \
  --write-out '%{http_code}\n' \
  --header 'Content-Type: application/json' \
  --header "X-Client-ID: ${MYSMPP_CLIENT_ID}" \
  --header "X-Token: ${MYSMPP_TOKEN}" \
  --data '{"from":"10690000","to":"+285032768252","text":"safe rate test"}' \
  "http://${MYSMPP_HOST}:${MYSMPP_HTTP_PORT}/v1/messages" \
  | sort | uniq -c
```

预期同时看到 `400` 和 `429`：通过令牌桶的请求在目标号码校验处返回 400，超出 40 TPS/Burst 的请求返回 429。由于令牌会在测试执行期间持续补充，通过数可能略高于 40。

### 11.2 日额度测试

建议使用 `tenant-b`，每日额度为 500 分片且 100% 进入 stub：

1. 先发送少量 1 分片短信，确认 HTTP/SMPP 均能成功受理。
2. 混合使用 HTTP 和 SMPP，累计受理到 500 个分片。
3. 再发送 1 分片短信。
4. HTTP 应返回 429；SMPP 应返回 `0x00000058`。
5. 重复一个已成功的 HTTP `client_msg_id`，应返回原 `gateway_id`，不能再次扣额度。
6. 北京时间次日 `00:00` 后首次提交使用新的自然日额度记录。

额度按受理分片累计，后续上游失败不返还。测试人员不要直接修改 `tenant_quota_usage`；需要重置测试数据时由环境管理员先备份并执行受控操作。

### 11.3 跨协议共享验证

`tenant-b` 的 HTTP 和 SMPP 子账号绑定同一个主租户：

- HTTP 与 SMPP 合计持续速率上限为 60 TPS，不是各自 60 TPS。
- HTTP 与 SMPP 合计每日上限为 500 分片，不是各自 500 分片。
- 任一协议消耗的额度都会减少另一协议当天可用额度。

## 12. 测试验收清单

- [ ] `/healthz` 返回 `status=ok`。
- [ ] HTTP 正确凭据返回 202，错误 Token 返回 401。
- [ ] HTTP 重复 `client_msg_id` 返回相同 `gateway_id`。
- [ ] HTTP 只能查询本账号消息。
- [ ] SMPP `bind_transceiver` 成功，错误密码返回 `0x0000000E`。

## 13. 配置修改与生效手册

### 13.1 三处配置必须同时正确

新增或调整主租户时，至少核对：

1. `tenants[]` 中存在唯一的主租户及 limits。
2. `clients[].tenant_id` 把 HTTP 子账号绑定到主租户。
3. `esmes[].tenant_id` 把 SMPP 子账号绑定到主租户。

只增加 `tenants[]` 而不绑定子账号不会自动按同名关联。只给子账号填写 `tenant_id` 但漏掉对应 `tenants[]`，该子账号会按禁用租户拒绝提交。

### 13.2 推荐生效方式

可通过管理后台分区页面更新：

```text
/admin/tenants
/admin/clients
/admin/esmes
```

也可通过管理员鉴权的完整配置 API 更新：

```text
PUT /v1/config
```

配置 API 是完整替换，不是 JSON Merge Patch。禁止只发送本手册中的 `tenants` 局部片段，否则会丢失 Provider、路由、存储和其他配置。

推荐操作顺序：

1. 查看 `/healthz`，确认 storage 正常、outbox/pending 已回落。
2. 备份当前完整 `config.json`，记录 SHA-256 和文件权限。
3. 在完整配置副本上修改 `tenants`、`clients[].tenant_id`、`esmes[].tenant_id`。
4. 校验所有 tenant ID 唯一，账号引用的 tenant ID 全部存在。
5. 通过后台或 `/v1/config` 提交完整配置。
6. HTTP 返回成功后重新读取配置，核对数值和绑定。
7. 检查 `/healthz`、管理后台 `/admin/connections` 和应用日志。
8. 再执行一条安全限流测试，确认运行时 resolver 已更新。

### 13.3 热更新何时生效

通过管理后台或 `/v1/config` 更新时：

- 先执行 `Normalize()` 和 `Validate()`；非法数值、重复 tenant ID、无效时区等会拒绝更新。
- 校验通过后立即替换运行时租户 resolver 和 limiter，不需要重启容器。
- 成功后的下一次新提交立即使用新租户配置。
- 配置会原子写回 `config.json`，旧文件保留为同目录 `.bak`。
- 完整配置热更新也会重建 Provider registry，上游 SMPP 连接会重新 bind；应在低峰操作，并确认连接恢复为 `bound`。
- 热更新时租户令牌桶会重建为满桶，因此配置变更瞬间可重新获得一个完整 Burst。

直接在宿主机上编辑 `config.json` 不会被运行中进程自动监听。直接文件修改只有在容器重启后才会加载，不推荐作为常规更新方式。

### 13.4 重启后的行为

| 数据/状态 | 容器重启后的行为 |
|---|---|
| tenants 和账号绑定 | 从持久化 `config.json` 重新加载 |
| TPS token bucket | 进程内状态丢失，重新以满 Burst 启动 |
| PostgreSQL 日额度 | 持久化保留，不会因应用重启清零 |
| messages/outbox/pending | PostgreSQL 持久化保留 |
| SMPP sessions | 断开，客户端需要自动重连/rebind |
| 上游 SMPP binds | 应用启动后自动重连 |

测试环境使用 PostgreSQL，因此日额度不会因 mysmpp 重启重置。如果 storage 使用 memory driver，日额度会随进程重启清零，不能用于要求硬额度的环境。

### 13.5 配置变更后的最小验收

| 检查 | 通过标准 |
|---|---|
| 配置读取 | `tenants` 数量、TPS、Burst、日额度、时区正确 |
| 账号绑定 | HTTP/SMPP 子账号指向预期 tenant ID |
| 服务健康 | `/healthz` 返回 `status=ok` |
| 上游连接 | `/admin/connections` 显示全部预期 Provider 为 `bound` |
| TPS | 超限出现 HTTP 429 / SMPP `0x58` |
| 额度 | 达上限后拒绝，数据库 used_segments 不超过 limit |
| 数据一致性 | 拒绝请求不新增 message/outbox，不调用 Provider |

## 14. 运维核查与额度查询

以下命令需要服务器运维权限。测试人员不应获得数据库或 Docker 权限。

### 14.1 查询各租户每日额度使用量

```bash
docker exec -u postgres mysmpp-postgres \
  psql -U mysmpp -d mysmpp -v ON_ERROR_STOP=1 -P pager=off -c "
SELECT tenant_id, quota_date, used_segments, updated_at
FROM tenant_quota_usage
ORDER BY quota_date DESC, tenant_id;"
```

带配置上限和剩余额度的当前表：

```sql
SELECT
  tenant_id,
  quota_date,
  used_segments
FROM tenant_quota_usage
WHERE quota_date = (CURRENT_TIMESTAMP AT TIME ZONE 'Asia/Shanghai')::date
ORDER BY tenant_id;
```

数据库只保存 `used_segments`，配置上限仍以当前 `config.json` 的 `tenants[].limits.daily_segments` 为准。计算剩余额度时必须同时读取当前配置；不能假设历史上限和当前上限相同。

### 14.2 查询租户消息记录

```bash
docker exec -u postgres mysmpp-postgres \
  psql -U mysmpp -d mysmpp -v ON_ERROR_STOP=1 -P pager=off -c "
SELECT id, tenant_id, account_id, client_msg_id, provider, state, submitted_at
FROM messages
WHERE tenant_id = 'tenant-b'
ORDER BY submitted_at DESC
LIMIT 50;"
```

可以据此确认 HTTP/SMPP 是否写入相同 `tenant_id`，以及 HTTP 的 `client_msg_id` 是否正确保存。

### 14.3 识别拒绝原因

CDR rejected 事件中的租户相关 reason：

| reason | 含义 |
|---|---|
| `tenant_disabled` | 主租户禁用或子账号引用不存在的主租户 |
| `tenant_tps` | 主租户令牌桶没有可用 token |
| `tenant_daily_segments` | 本次受理会超过主租户日分片额度 |

HTTP 的 TPS 和额度都返回 429；SMPP 都返回 `0x00000058`。协议返回码无法区分 TPS 与日额度，需要结合 CDR reason、额度表和请求速率判断。

### 14.4 健康检查边界

`/healthz` 能确认 storage、SMPP listener、outbox depth 和 pending size，但不会显示：

- 各租户当前 token 数。
- 各租户当日已用/剩余分片。
- 上游 SMPP Provider 是否全部 bind。

因此限流限额验收不能只看 `/healthz`，还要结合提交返回码、CDR、额度表和 `/admin/connections`。

## 15. 回滚说明

本次租户配置变更前的独立备份位于：

```text
/root/mysmpp-backups/20260819-175726-pre-tenant-200tps/config.json
```

该备份没有 `tenants` 和账号 `tenant_id` 绑定，回滚后 A/B/C 会恢复成 HTTP/SMPP 各自独立、默认不限 TPS/不限日额度的兼容身份。因此，只有在明确需要撤销租户限制时才能使用。

5. 注意：删除租户配置不会删除历史 `tenant_quota_usage`、messages 或 CDR；历史审计记录必须保留。
