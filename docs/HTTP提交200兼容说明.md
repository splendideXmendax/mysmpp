# HTTP 提交成功返回 200（v1.2.3）

## 变更和边界

`POST /v1/messages` 成功受理由 `202 Accepted` 改为 `200 OK`，包括首次提交和相同 `client_msg_id` 的幂等重试。带 Dispatcher 的正常链路与无 Dispatcher 的兼容链路统一调整。生产代码仅修改 `internal/httpgw/rules.go` 的两处成功状态码。

200 表示网关成功受理；短信仍异步发送，不代表供应商已接受或手机已收到。最终结果继续通过查询和 DR 确认。幂等重试返回原 `gateway_id`，可能包含已经更新的消息状态，不保证整个 JSON 与首次响应逐字相同。

响应 JSON 字段、鉴权、校验、租户 TPS/额度、短信路由、分片绑定、SMPP 协议和 DR 投递逻辑均不改。没有新配置项、依赖或数据库迁移。测试环境保留既有 HTTP DR 精确转发规则，HTTP/HTTPS 回调继续按原规则执行。

| 场景 | 状态码 |
|---|---|
| 成功受理、幂等重试 | 200 |
| 非法参数、目的号码或超长短信 | 400 |
| 凭据无效 | 401 |
| 租户禁用或明确禁止 | 403 |
| TPS、日额度或入口频率限制 | 429 |
| Dispatcher 同步提交失败 | 502 |
| 无 Dispatcher 链路存储失败 | 500 |

错误码维持原有映射；不能把所有 HTTP 响应强制转换成 200。上游异步失败仍通过消息状态及 DR 呈现。

## 客户与测试适配

测试脚本改为断言 `response.status_code == 200`，并检查响应中的 `gateway_id`。使用相同账号和 `client_msg_id` 重试时应返回同一个 ID，不重复创建消息或扣日额度。历史版本切换期间可接受 200/202 两种成功码，但 v1.2.3 验收必须明确断言 200。

此前修复报告中的 202 保留为当时版本的现场记录；当前 API 文档和用例已同步为 200。

## 测试环境验收方法

1. 备份现有 mysmpp 配置和容器信息，构建独立镜像，仅替换 mysmpp，保留回滚容器。
2. 使用仅路由到测试桩的 tenant-c 提交短短信和长短信，各重试一次：四次响应都为 200，重复 ID 对应同一 gateway_id。
3. 核对 HTTP 接收端真实日志与持久化 delivery 完成状态，长短信每片 DR 均到达。
4. SMPP 乱序提交同一 UDH 长短信的三片，检查同一路由/供应商，三个 submit_sm_resp 及三个 DR 均成功。
5. 核对错误 Token 仍为 401、非法回调协议仍为 400；不通过耗尽实际客户额度来测试 429，额度回归在隔离单元测试中完成。
6. 比较部署前后配置 SHA256，以及其他服务容器 ID/启动时间，确认不变。检查 mysmpp 健康、上游绑定和新异常日志。

回滚时仅恢复先前 mysmpp 镜像/容器；不修改数据库或配置。回滚后提交成功码恢复为 202，客户端须知悉此差异。
